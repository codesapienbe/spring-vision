01 What's actually in the access token

Keycloak issues a standard JWT via the client_credentials grant — no human user or password involved, the caller is a service account tied to a client. A real token carries far more than realm_access.roles, but the app only reads one of these claims.

→ Practical effect: any validly-signed, non-expired token from this realm counts as "authenticated." Whether it can call a specific tool comes down entirely to whether realm_access.roles contains mcp-admin — checked by a manual SecurityContextHolder read in VisionTool.requireAdminRole(), not Spring's declarative @PreAuthorize (unreliable on @Tool methods in current Spring AI — see spring-projects/spring-ai#2356).

→ Design intent: mobile's token lives 24× longer than desktop's because the app has no refresh flow — so it deliberately does not get mcp-admin. If it ever leaked, the blast radius stays capped to general-purpose tools; biometric enrollment, threat detection, and PII-document recognition stay off it.
